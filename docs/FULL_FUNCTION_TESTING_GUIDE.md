# 全功能检测指导手册：真实网页操作与项目助手验收

适用产品：AI 项目管理 Agent。编写日期：2026-09-10。  
适用人员：产品验收人员、人工测试人员、前后端开发者、具备浏览器操作能力的自动化 Agent。  
本手册根据当前网页路由、表单、业务手册和权限边界编写。**这是测试执行规范，不是“所有功能已测试通过”的报告。** 测试开始前必须记录实际版本和部署状态。

产品边界参见 [项目手册](HANDBOOK.md)。Copyright 2024–2026 Jack Zhang，遵循仓库 Apache License 2.0 及 NOTICE。

## 1. 怎样使用这份手册

按以下顺序执行：

1. 填写环境登记表，确认测试的是哪一版前端、后端和数据库。
2. 准备角色账号、独立测试项目和可核对的数据台账。
3. 执行第 5 节的网页主流程，确认关键路径可用。
4. 执行第 6–10 节的功能、权限、异常、助手和并发用例。
5. 按第 11 节保存证据，登记每一项的实际状态。
6. 按第 12 节判断是否达到本次发布门槛，最后清理测试数据。

检测包含三个层次，结论必须注明完成到了哪一层：

| 层次 | 操作方式 | 能证明什么 |
| --- | --- | --- |
| 网页真实操作 | 在浏览器点击、输入、选择日期、提交、取消、刷新、返回和删除 | 用户是否能完成实际业务流程 |
| 接口与事实核验 | 检查网络响应；必要时只读核对接口或测试数据库 | 页面提示是否对应真实、完整、正确的持久化结果 |
| 故障与自动化回归 | 多账号、多标签页、网络中断、服务故障、确定性测试 | 异常、竞争条件和重复操作下是否可靠 |

**调用接口成功不能代替网页操作成功；页面弹出“成功”也不能代替业务数据核对。**

## 2. 测试前准备

### 2.1 环境登记表

复制填写；不要把密码、令牌或密钥写入报告。

```text
测试批次：QA-YYYYMMDD-序号
执行人／执行 Agent：
开始时间／结束时间／业务时区：
BASE_URL：测试环境浏览器入口
前端版本／镜像标识：
后端版本／镜像标识：
数据库 migration head：
浏览器版本／操作系统：
视口：桌面 1440×900；平板 820×1180；手机 390×844
LLM：真实模型／Stub；模型名；是否记录 token 与费用
Worker／定时调度／Redis：正常／未启动／本轮故障注入
通知渠道：console／测试收件箱／已批准的测试渠道
OA／企业微信登录：已配置／未配置／本轮不测
测试账号别名及角色：
本轮允许修改或删除的对象范围：
证据存放位置：
```

入口使用部署配置中的 Nginx 地址，不把 `3000`、`8000` 或某个端口当成所有环境的固定入口。真实网页测试应经过用户实际使用的入口，以覆盖代理、鉴权和 SSE。

### 2.2 版本与可用性检查

- 确认前后端部署了待验收代码；仅修改工作区源码不代表容器已经更新。
- 确认迁移已执行且只有一个 head。涉及新增执行计划表的版本，缺迁移时不能测出有效的助手批次结果。
- 打开首页及登录页；确认 `/health` 和 `/health/ready` 可用。
- 记录 LLM 是否真实配置。Stub 结果不能作为模型理解、多指令规划或真实工具选择准确率的证明。
- 确认 Worker 与定时调度状态。需要异步分析、风险扫描或通知的用例应能观察到任务完成或明确失败。
- 每个角色使用独立浏览器上下文。不要通过同一个标签页来回换令牌模拟并发用户。
- 测试期间固定版本。若代码、路由、迁移或测试目录发生变化，划分新批次，重跑受影响用例。

### 2.3 数据与删除范围

使用独立测试环境；在共享环境只能操作明确标记的测试数据。所有新增名称带本批次前缀，例如 `QA-20260910-A-联调验收`。

| 数据 | 建议准备 | 用途 |
| --- | --- | --- |
| 账号 | 管理员 A、管理层 E、项目负责人 P1/P2、成员 M1/M2、停用账号 X | 正常权限、跨项目越权、停用后访问 |
| 项目 | P1 负责的项目 A；P2 负责的项目 B；空项目 C | 正常流程、跨项目隔离、空态 |
| 执行任务 | A 中至少 12 项，分属不同负责人和状态 | 列表、筛选、统计、进度提交 |
| 日期 | 昨天、今天、明天、本周末、下周一、无截止日期 | 超期与日期边界 |
| 完成度 | 未知、0、1、50、99、100 | 数值边界；未知不等于 0 |
| 同名数据 | 同项目两个“联调验收”；另一个项目也有同名任务；两名同姓名用户 | 名称解析与歧义拦截 |
| 依赖与路线 | A→B→C 依赖链；一条备用路线；一个里程碑 | 预览、回滚、依赖阻断、统计去重 |
| 汇报 | 窗口内 3 条、窗口外 1 条；至少 1 项无汇报 | “最近进展”的事实覆盖 |
| 问题与行动项 | 开放／已解决问题；未完成／已完成行动项 | 闭环、过滤、权限 |
| 删除专用 | 一个无关联任务、一个有关联记录的任务、一个专用项目 | 取消删除、确认删除、关联数据校验 |

建好数据后保存台账：对象类型、真实 ID、项目代码、名称、负责人 ID、状态、日期、完成度、关联对象 ID、创建批次。后续预期结果依据台账计算，不能照抄被测助手的回答。

**禁止使用清空全库、批量删除所有项目等方式清理一次测试。** 清理只处理本批次 ID 台账中的对象。涉及外部通知，仅使用登记的测试收件人。

当前界面可见的删除与非删除行为：

| 对象 | 检测入口 | 应核对的边界 |
| --- | --- | --- |
| 项目 | 项目详情的管理区域 → 删除项目 | 页面声明永久删除关联数据；需要原因；仅具备对象权限者可操作 |
| 任务 | 任务详情 → 删除任务 | 需要原因；关联进展、问题等按业务规则处理并审计 |
| 助手记忆 | 助手记忆面板 | 删除本人可管理的记忆；不能误删业务对象 |
| 对话 | 对话列表 → 归档 | 验证归档语义；不能宣称已物理删除 |
| 用户 | 用户管理 → 状态 | 验证停用与身份访问；不要把停用当作删除 |
| 助手业务工具 | 输入删除项目／删除任务指令 | 按产品边界拒绝直接执行破坏性工具，并核对数据未变 |

对没有网页入口的能力，记录“网页未提供入口”。即使后台有 API，也不能把 API 测试记为该网页功能通过。

## 4. 每个表单都要执行的通用检查

下面的动作矩阵适用于新建项目、任务、用户、计划资料、进展、问题、记忆、删除原因等表单；不适用项注明原因。

| 编号 | 操作 | 预期检查 |
| --- | --- | --- |
| FORM-01 | 空表单直接提交 | 必填项附近显示明确错误；没有创建记录 |
| FORM-02 | 输入空格、换行、制表符后提交 | 不能形成“看似有字”的空名称／空内容 |
| FORM-03 | 输入中文、英文、数字、标点、emoji、多行文本 | 正确保存和展示；不能乱码或截断关键内容 |
| FORM-04 | 在当前字段上限的 L−1、L、L+1 长度提交 | 前后端边界一致；超长有明确提示；保留可修正输入 |
| FORM-05 | 输入数值上下限及上下界之外的值 | 不允许负工期、超过 100 的完成度等非法状态 |
| FORM-06 | 起始日期晚于结束日期；清空可选日期 | 无效组合拒绝；未知日期保持未知 |
| FORM-07 | 输入重复唯一标识，例如项目代码、用户名 | 说明重复字段；不产生第二条同标识记录 |
| FORM-08 | 填完后取消、点击关闭、按 Esc | 没有后台写入；再次打开的草稿策略一致 |
| FORM-09 | 按 Enter、点击提交、连续双击提交 | 不产生意外重复记录；加载期间状态清楚 |
| FORM-10 | 提交成功后刷新页面，重新登录再查看 | 数据真实持久化；不是本地状态假成功 |
| FORM-11 | 提交返回 400/403/409/422/500 或断网 | 不显示成功；可理解错误；不会悄悄清空整份输入 |
| FORM-12 | 键盘 Tab／Shift+Tab 操作全部字段与按钮 | 焦点可见；弹窗不把焦点困在不可操作区域 |
| FORM-13 | 使用中文输入法组合输入并按 Enter | 选字不会被误判为提交／发送 |
| FORM-14 | 输入 `<script>` 样式文本、Markdown、链接 | 文本按产品预期显示，不能执行脚本或泄露登录态 |

字段长度以当前表单与后端 Schema 的实际限制为准；没有明确限制时记录“待定义”，不要随意给产品编造约束。

## 5. 真实点击主流程：从新建到删除

以下流程必须通过浏览器完成。接口只用于额外核对结果。

### 5.1 登录并建立测试项目

1. 用 P1 打开 `/login`，输入登记的测试账号和密码，点击登录。
2. 确认姓名、角色、菜单与当前身份一致；刷新后仍正确。
3. 点击“项目”，进入项目列表；点击新建入口。
4. 第一次空表单提交，截图必填错误并确认未创建项目。
5. 填入台账中的项目代码、名称、负责人和日期，点击提交一次。
6. 记录成功提示、跳转地址和新项目 ID。
7. 回列表搜索代码；打开详情；刷新，核对所有字段。
8. 尝试再次创建相同代码，验证重复校验及项目总数不变。

通过条件：仅新增一条正确项目；表单、列表、详情、刷新后的结果一致。

### 5.2 新建任务并提交进展

1. 在项目详情点击“新建任务”。
2. 填任务名称、所属工作流、负责人 ID 和起止日期；负责人必须取自台账。
3. 提交后核对任务 ID、负责人姓名、项目归属和日期。
4. 用 M1 登录，“我的任务”应只展示符合本人负责口径的任务。
5. 打开该任务 → 更新进展，输入：`QA 批次：接口联调完成，待验收；目前没有请求调整截止日期。`
6. 提交，不勾选完成标记；核对汇报原文已保存，计划日期未被改动。
7. 观察异步分析完成或明确失败。即使 AI 失败，原始汇报也应仍存在。
8. 再提交一条明确完成汇报并使用页面的完成标记；核对状态与相关页面统计。
9. 用 M2 重复访问该任务，验证越权查看或提交按实际权限被拒绝。

通过条件：汇报、任务状态、AI 分析状态区分清楚；“可能延期”不能自动成为改计划授权。

### 5.3 计划、风险、问题、行动项与通知闭环

1. 进入项目的“计划资料与路线”，建立两项任务依赖，查看依赖关系。
2. 修改会影响下游日期的参数，先预览；记录预览前后数据库事实未变化。
3. 查看冲突、工期、日期差异、影响任务，再通过产品指定的确认流程执行。
4. 执行后刷新计划与任务详情，核对实际差异只包含确认内容。
5. 进入“风险与建议”，核对风险原因、依据和首次发现时间。
6. 通过项目或任务提供的问题入口登记问题；打开 `/issues/{id}` 核对。
7. 检查建议的证据来源；采纳、驳回、生成行动项等仅按当前页面授权入口执行。
8. 完成行动项并检查问题闭环，不能把“建议生成”视为“问题解决”。
9. 用测试收件人打开通知中心，确认收到对应通知；本人确认后记录确认状态。
10. 换另一个账号，验证不能替收件人确认。

通过条件：事实、预测、建议、用户确认和实际执行分别可追踪。

### 5.4 删除任务：先取消，再确认

1. 打开台账中的删除专用任务，记录 ID、所属项目及关联记录数量。
2. 点击“删除任务”，核对弹窗显示的是该任务名称。
3. 不填删除原因尝试确认：应提示校验失败，数据仍存在。
4. 填入本批次删除原因，点击取消：刷新后任务及关联数据仍存在。
5. 重新打开删除弹窗，填写原因并点击“确认删除”一次。
6. 检查跳转和成功提示；从列表搜索该任务，再访问旧详情 URL。
7. 核对任务已不可访问；关联进展、问题等按声明的规则删除／处理，没有孤儿引用。
8. 检查删除审计至少能关联操作者、对象、时间和原因；不要只检查提示框。
9. 用无权限账号重跑删除入口与请求校验，应拒绝且数据不变。

### 5.5 删除项目与测试数据清理

仅对删除专用项目执行：项目详情 → 管理区域 → 删除项目 → 核对名称 → 填写原因 → 确认删除。

核对项目及任务、问题、风险等关联数据符合页面声明；其他项目、账号、通知收件人不能受影响。删除后使用旧链接应得到正常的不存在／无权提示，不能白屏。

若测试暴露关联删除不完整，停止对该项目重复清理，保留 ID 和证据用于定位；不要用手工 SQL 清空数据来让用例“通过”。

## 6. 模块专项用例清单

每项均记录 PASS／FAIL／BLOCKED／NOT_RUN／N/A，并保存必要证据。

### 6.1 登录、角色、用户管理

| ID | 实际操作 | 核验重点 |
| --- | --- | --- |
| AUTH-01 | 正确账号登录、退出、浏览器后退 | 退出后不能恢复受保护数据或写入权限 |
| AUTH-02 | 错误密码、不存在账号、空输入 | 清楚提示；不能泄露敏感身份信息 |
| AUTH-03 | 停用账号登录；登录中由管理员停用再操作 | 服务端权限有效，不只隐藏按钮 |
| AUTH-04 | 登录过期后打开详情、提交表单、发送助手消息 | 引导重新登录；不显示假成功 |
| AUTH-05 | 两个角色分别查看导航并直接输入受限 URL | 普通成员无管理看板入口；仅管理员可管理用户；后台同样校验 |
| USER-01 | 管理员新增用户，刷新列表、用该账号登录 | 角色、状态、姓名及身份对应正确 |
| USER-02 | 编辑角色／部门／邮箱／手机 | 输入校验与刷新后的字段一致 |
| USER-03 | 重复用户名、非法邮箱、弱密码及两次密码不一致 | 错误明确；没有半创建账号 |
| USER-04 | 重置测试账号密码，用新旧密码分别登录 | 新密码有效，旧密码失效 |
| USER-05 | P1、E、M1 直接访问用户管理与写入接口 | 不能管理用户或提升本人角色 |
| AUTH-06 | 已配置 OA／企业微信时走真实登录回调 | 有效、过期、重复、参数缺失分别有合理结果 |
| USER-06 | 在允许的测试身份源上执行 OA 同步 | 同步数量可核对；OA 只读；不因同步扩大本地权限 |

### 6.2 项目、任务、列表、看板

| ID | 实际操作 | 核验重点 |
| --- | --- | --- |
| PRJ-01 | 修改名称、目标、负责人；保存后刷新 | 所有修改持久化；未提交字段不被重置 |
| PRJ-02 | 一次提交包含有效改期和无效负责人 | 整次修改失败时不留下部分改期 |

原子批次中已回滚的项目不能计为成功；查询动作的成功也不能充当任务创建成功数。

### 7.5 多角色、多次运行与评分

- 确定性用例固定数据与工具结果，验证调度、事务、权限、恢复。
- 真实模型用例建议每个场景至少跑 3 次；关键写入场景再按 A、P1、E、M1 覆盖。这个次数是起始采样建议，不代表统计充分性。
- 每次新建独立测试数据或唯一名称；不能让上次的同名记录影响本次结论。
- 管理员成功而管理层被正确拒绝，均可算各自用例通过；“所有角色都能写入”不能作为成功标准。

分别报告：指令项提取正确率、实体绑定正确率、允许写入的完成率、应拒绝操作的拦截率、遗漏率、重复写入率、恢复后重复率、查询事实准确率、时间口径准确率、端到端 P50/P95。

每个指标给出分子、分母和样本条件。真实模型结果与脚本化工具结果分开，不将一次成功表述为能力稳定可靠。

## 8. 权限、并发和故障测试

### 8.1 权限操作矩阵

至少对“查看项目、查看任务、创建任务、更新进度、修改计划、删除任务、删除项目、查看历史、查看／恢复执行清单、通知确认、管理用户”执行以下组合：

1. 有权限角色操作本项目对象。
2. 同角色操作别人项目的对象。
3. 无权限角色在网页尝试。
4. 无权限角色直接访问对象 URL／重放已记录的请求。
5. 请求提交前有权限，真正执行或恢复前撤销权限。

角色只是第一层依据；还要核对项目负责人、任务负责人、成员关系、对象状态和方案确认者。用当前 `backend/app/core/permissions.py` 与产品规则生成预期矩阵，不能简单假设“项目负责人能改任何项目”。

### 8.2 两人或两个窗口的竞争场景

| ID | 场景 | 结果要求 |
| --- | --- | --- |
| CON-01 | 两人同时修改同一对象的不同／相同字段 | 按产品并发策略合并或拒绝；不能无提示丢失更新 |
| CON-02 | 两人确认同一变更方案 | 只执行一次或明确冲突 |
| CON-03 | 一人删除任务，另一人提交进展 | 明确失败或按事务顺序成功；无孤儿汇报 |
| CON-04 | 两窗口恢复同一批次 | 不重复执行成功项 |
| CON-05 | 一个窗口停止生成，另一个窗口收到迟到结果 | STOPPED／INTERRUPTED 不被无条件改回成功 |
| CON-06 | 删除项目时后台分析／风险扫描正在执行 | 后台能识别对象失效，不创建悬空数据 |

### 8.3 故障注入

只在登记的测试环境中执行，记录故障开始和恢复时间。

| 故障 | 测试动作 | 核验 |
| --- | --- | --- |
| 浏览器断网 | 写入提交前、提交中、收到响应前三个时点分别断网 | 区分未提交与结果未知；重试不盲重复 |
| API 4xx／5xx | 对测试请求制造拒绝或服务错误 | 页面错误状态、输入保留、无假成功 |
| LLM 超时／无效 JSON | 助手查询与写入分别触发 | 写入前规划失败不产生动作；部分执行有账本 |
| Worker 停止 | 提交进展、生成建议、产生通知 | 原始业务数据保存；异步状态准确；恢复后可继续 |
| Redis 不可用 | 触发需排队能力 | 不把排队失败说成已分析／已投递 |
| 后端重启 | 执行前、中途、写入后但回执前分别重启 | 已完成、未执行、结果未知可区分；恢复不重复 |
| 数据库拒绝／事务失败 | 原子批次中制造受控约束失败 | 批次完整回滚；其他独立请求不被误回滚 |

重启与断网必须记录注入时点。如果没有证据表明命中了“写入后、回执前”，不能宣称该窗口已经覆盖。

## 9. 浏览器体验、性能与可访问性

- 桌面、平板、手机至少各跑一次登录 → 列表 → 详情 → 提交 → 返回。
- 检查侧边导航、移动导航、弹窗、日期选择器、表格和助手长回复是否溢出。
- 验证滚动后按钮可达，软键盘弹出时输入框和发送按钮可用。
- 检查弹窗焦点、标签与输入的关联、按钮名称、加载提示、错误提示可见性。
- 助手流式输出时用户手动向上滚动，不应持续被强制拉回底部。
- 错误页、空列表、长任务名、长负责人名与超长 Markdown 分别截图。
- 记录首次可操作时间、列表加载、普通提交、SSE 首 token、工具执行和最终落库时间。
- 性能阈值由项目方登记为本轮目标；没有既定 SLO 时给实际分布，不能自创“超过 2 秒就是缺陷”。

## 10. 交给自动化 Agent 的执行要求

### 10.1 自动化实现原则

本仓库当前前端脚本有 `typecheck`、`lint`、`build`；不要假设已存在可直接运行的 Playwright 测试命令。是否安装浏览器驱动和测试框架，应先检查当前项目依赖。

- 网页用例使用真实浏览器。API 可用于准备测试夹具、只读核验与清理，但不能替代被测的点击和填写步骤。
- 定位优先使用可访问角色、标签和稳定测试标识，例如按钮名“新建任务”“确认删除”；不依赖屏幕坐标和第几个同名按钮。
- 多角色分别保存独立登录状态，敏感认证文件不纳入版本库。
- 等待具体页面状态、请求响应或记录出现，不用固定长 sleep 假装同步成功。
- 对 SSE 等待终态或明确失败；不能因 HTTP 200 就判定整轮成功。
- 失败保留截图、视频／trace、必要网络摘要与本轮测试数据 ID。隐藏令牌、密码、Cookie 和个人敏感信息。
- 自动重试只能处理已知的测试基础设施瞬时失败。对写操作结果未知，不自动重放整条用例。
- 新增 UI 测试从登录、新建项目、新建任务、提交进展、删除取消／确认、助手停止／恢复六条主链开始。

### 10.2 可直接复制的检测任务说明

```text
请依据 docs/FULL_FUNCTION_TESTING_GUIDE.md 检测当前项目。

环境：填写 BASE_URL、版本、业务时区。
账号：通过安全方式提供 A/E/P1/P2/M1/M2 的测试登录方式。
允许写入和删除：仅本批次 QA-YYYYMMDD-序号 标记、且记录真实 ID 的测试对象。
外部通知：仅指定测试收件人；未配置能力标为 BLOCKED 或 N/A 并解释原因。

执行要求：
1. 先读项目手册、当前 AGENTS.md 和本检测手册，核对真实页面与版本。
2. 建立数据台账和用例执行表，然后进行真实浏览器点击、输入、提交、取消、刷新。
3. 覆盖正常、边界、越权、重复提交、并发、断网和恢复；关键模块不能只看页面。
4. 写操作后核对持久化事实。助手逐项核对原文、对象 ID、依赖、状态和计数。
5. 未执行的用例不得记 PASS；不能用接口调用替代真实网页用例。
6. 能独立继续时继续检测；记录阻塞原因，不为凑覆盖率编造结果。
7. 代码和部署变化时划分新批次，不混用旧结果。
8. 输出执行表、缺陷表、证据索引、权限矩阵、助手评分、未覆盖清单和回归建议。
9. 测试结束只清理台账内的测试数据；保留复现缺陷所需的隔离数据及说明。

本任务只做检测和报告。发现缺陷后先提交可复现证据，修复作为单独任务处理。
```

PASS 需要实际执行且结果符合预期；BLOCKED 是条件不足无法判断；NOT_RUN 是尚未执行；N/A 需要写清产品边界或环境原因。任何一项都不能通过改标签消除失败。


建议分级：P0 为越权破坏、严重数据泄露或大范围错误删除；P1 为关键流程不可用、错误对象写入、重复写入或原子性失效；P2 为局部功能错误、错误统计、可规避失败；P3 为文案、布局或轻微体验问题。严重级别与修复优先级可以不同，但要写明依据。

### 11.3 最终检测报告结构

1. 本次版本、环境、时间、角色和数据范围。
2. 按模块列计划用例、已执行、通过、失败、阻塞、未执行、不适用数量。
3. 关键业务闭环及真实网页操作覆盖。
4. 缺陷列表，先列 P0/P1，再列其他问题。
5. 助手专项结果：确定性执行与真实模型结果分开。
6. 权限与并发结果、故障注入命中窗口和恢复结果。
7. 性能数据、截图和证据索引。
8. 未覆盖范围、剩余风险、是否满足本次发布门槛。
9. 清理记录与保留数据说明。

同时报告“执行覆盖率＝已执行用例／计划适用用例”和“通过率＝通过用例／已执行用例”。对 BLOCKED、N/A 的统计处理提前说明，不能只报告一个好看的通过率。

## 12. 建议验收门槛与执行节奏

以下为建议门槛，需由项目负责人结合发布范围确认：

- 登录、新建项目、新建任务、进展提交、计划确认、任务删除、项目删除、助手发送与停止等关键主链全部有真实网页证据。
- 本次发布范围内无未解决 P0/P1；关键权限用例不允许用“页面没按钮”代替服务端验证。
- 所有助手写入都能核对真实对象、成功数、失败数和未执行项；不允许假成功、错误对象写入或成功项重复执行。
- 原子批次失败时没有部分业务副作用；不支持的原子组合提前拒绝。
- 页面刷新、断网、停止和恢复后，状态与业务事实一致。
- 日期口径、查询分母、事实覆盖、截断与未知数据都明确。
- 未配置外部渠道与未完成真实模型评测必须列为未覆盖，不以 Stub 代替通过。
- 版本整理后被移除的历史测试不能算当前可复现的自动化覆盖；需要保留对应源码或重新建立测试。

建议分四轮：第一轮真实点击主流程；第二轮模块与权限；第三轮助手、并发、故障和恢复；第四轮缺陷回归与多角色真实模型复测。每轮结束先核对数据台账，再进入下一轮。
